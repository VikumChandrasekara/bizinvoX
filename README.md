# bizinvoX.com

Create a professional invoice in under a minute. Guests and free users can fully customize and download invoices on the Classic template for free, with a watermark, and remove the watermark from an invoice for $0.99. Pro ($5.99/month, or $52.47/year: 27% off) never has a watermark and unlocks all five templates.

|---|---|
| API | Rust · axum 0.7 · tokio · sqlx (PostgreSQL) · Redis (`ConnectionManager`) |

## Quick start

```bash
docker compose up --build
# web  -> http://localhost:3000
# API  -> internal (http://api:8080). Publish port 8080 in docker-compose.yml to reach /docs from the host.
```

Local development without Docker for the app processes:

```bash
# 1. Postgres + Redis
docker compose up -d postgres redis      # uncomment their `ports:` to reach them from the host
# 2. API
cd backend && cp .env.example .env && cargo run        # migrations run automatically
# 3. Web
cd frontend && cp .env.example .env.local && npm install && npm run dev
```

Payments need Stripe test keys (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_PRO_MONTHLY`, `STRIPE_PRICE_PRO_ANNUAL`). Without them, checkout returns `503 payments_unavailable` and everything else works. To forward webhooks locally:

```bash
stripe listen --forward-to localhost:8080/api/v1/webhooks/stripe
```

Make yourself an admin (for refunds and pricing): `UPDATE users SET is_admin = true WHERE email = '...';`

## How the tiers are enforced (server-side only)

| Capability | Guest | Free | Pro | Where it's enforced |
|---|---|---|---|---|
| Create invoice | Classic, customizable | Classic, customizable | any owned template | `templates::resolve_template_id` |
| Customize Classic (colors, fonts, removed fields, logo) | ✓ stored on the invoice | ✓ stored on the invoice | via templates | `invoices.layout_json`, `invoices.logo_png` |
| Create/edit templates, logo upload | — | — | ✓ | `require_pro` on every template write |
| Read a custom template | — | — | owner only | `GET /templates/{id}` → 403 unless Pro |
| Save invoices | browser + 48h guest row | ✓ dashboard | ✓ | `invoices.user_id` / signed guest cookie |
| Search, filters, CSV export | — | — | ✓ | `invoices::list`, `export_csv` |
| Download PDF | free, watermarked | free, watermarked | unlimited, clean | `payments::download` |
| Remove the watermark | $0.99 per invoice | $0.99 per invoice | n/a (never watermarked) | `payments::checkout` |
| Branding footer | shown | shown | removed | `render_pdf(is_pro)` |

The plan always comes from the database row loaded for the request, never from the JWT or the client. When a Pro subscription lapses, the account reverts to Free. Its templates and invoices are kept but locked, and rendering falls back to the invoice's own Classic customizations (or the plain Classic look).

Only Classic can be edited without Pro. The other four templates can be selected to preview, but the editor is read-only, and Download PDF and New invoice are disabled until the user returns to Classic. A free user's own Classic customizations are remembered while they preview a Pro template.

## Watermark removal flow

1. `POST /invoices/{id}/checkout` creates a `pending` payment and returns a Stripe Checkout URL.
2. Stripe sends `checkout.session.completed` to the webhook. The handler verifies the signature, checks the `idempotency:stripe:{event_id}` key in Redis, marks the payment `succeeded` and sets the invoice to `paid`.
3. Stripe redirects to `/checkout/success`, which calls `POST /invoices/{id}/checkout/confirm`.
   - If the webhook hasn't arrived yet, the API asks Stripe directly, server to server.
   - Either way, it mints a single-use token valid for 15 minutes. Only its SHA-256 hash is stored, in Postgres with a Redis mirror.
4. `POST /invoices/{id}/download {token}` checks that the token is unused, unexpired, tied to this invoice and backed by a succeeded payment, then returns a clean PDF.
   - Without a token the same endpoint is free: it returns the watermarked PDF, unless the invoice already has a succeeded payment (then it is clean, so a paid invoice can be downloaded again). A watermarked download does not lock the invoice.
   - It renders the PDF first, then consumes the token with an atomic conditional `UPDATE`, so a failed render doesn't burn it.
   - Each payment can mint up to 3 tokens, for retries.
   - A paid non-Pro invoice becomes **locked**, so one payment can't be reused for a different invoice. Users duplicate it to make changes.

Refunds (`POST /admin/payments/{id}/refund` or the `charge.refunded` webhook) revoke all unused tokens.

## Security

- **Passwords:** Argon2id (m=19 MiB, t=2, p=1 minimum, configurable) with a per-password salt inside the PHC string. Hashing runs on the blocking pool. Unknown-email logins still run a dummy verification, so timing doesn't reveal which emails exist.
- **Sessions:**
  - Short-lived JWT plus an opaque refresh token. Only the refresh token's hash is stored.
  - The refresh token is rotated on every refresh. Reusing an old one after a 15-second race grace period revokes the session.
  - Cookies are `HttpOnly`, `Secure` (outside dev) and `SameSite`. The refresh cookie is scoped to `/api/v1/auth`.
- **CSRF and Origin:** a double-submit CSRF token is required on every mutating route except signature-verified webhooks. Requests are also checked against an Origin allow-list, and CORS is locked to the frontend origin.
- **Rate limits:** a Redis sliding window implemented in Lua.
  - Login and signup: 10 per minute per IP.
  - Password-reset and verify-email: 5 per minute.
  - Invoice creation: 30 per minute. Checkout: 10. Downloads: 20.
  - Everything else: 300 per minute.
- **Input:** parameterized SQL only. Every request body uses `deny_unknown_fields` and `validator` rules. Money uses `numeric(12,2)` and `rust_decimal`, never floats.
- **Logo uploads:**
  - Type is detected from content, not the file extension. Only PNG, JPEG and WebP are accepted.
  - Limits: 1 MB file size, 4096 px per side, 64 MB decode allocation.
  - Every logo is decoded and re-encoded as PNG, which strips metadata and anything hidden in the original file.
- **Security headers:** CSP, HSTS (preload), nosniff, `frame-ancestors 'none'`, Referrer-Policy and Permissions-Policy on both the API and the web app.
- **Other:**
  - Guest invoices are keyed by HMAC-signed random UUIDs, and non-owners get 404, so drafts can't be enumerated.
  - CSV export guards against spreadsheet formula injection.
  - Stripe ids are validated before they're used in Stripe API URLs.

## Performance

- Rust API: async throughout, a pooled Postgres connection, and a multiplexed Redis connection.
- PDF rendering and Argon2 run on the blocking pool. PDFs render in milliseconds, so no job queue is needed.
- Redis caches the default template, Pro templates, pricing and session checks.
- Release builds use `lto = "fat"` and `codegen-units = 1`. The runtime image is distroless and non-root.
- Next.js:
  - Marketing, template and guide pages are prerendered (SSG).
  - The builder and editor are client-side and code-split.
  - Fonts are self-hosted through `next/font`.
  - The live preview is debounced at 180 ms and autosave at 1.2 s.

## The editor

The site is one page, plus two legal pages linked from the footer: `/privacy` (Privacy Policy) and `/terms` (Terms & Conditions). The invoice itself is the editor: click any text and type, with no form fields.

- **Templates popup:** the nav "Templates" link (and the Templates button above the invoice) opens a dialog with five templates (Classic, Modern, Elegant, Bold, Typewriter), each a live miniature of the real renderer. Picking one applies it and closes the dialog.
- **Center:** the A4 invoice. Names, addresses, line items, dates, currency, notes, title and footer are all edited in place. Totals are calculated exactly as the server does.
- **Removing fields (Pro):** hover or focus a field (address, email, phone, tax ID, due date, notes, footer and so on) and click the X to remove it, or the X on the TAX / DISC. table headers to drop a column. Removed fields disappear from the PDF as well and can be restored from the right panel ("Removed fields"). Guests and Free accounts see the X, but clicking it shows an upgrade prompt and changes nothing. The list is stored as `hiddenFields` in the template layout and validated server-side against an allow-list (`HIDEABLE_FIELDS` in `backend/src/models.rs`).
- **Right panel:** changes with what you click.
  - Text: the content, plus font and color.
  - Logo: upload, remove and position.
  - Header: style, colors and logo position.
  - Line-item table: columns, row spacing and header color.
  - Totals: colors.
  - Nothing selected: the whole design, and a reset.
- **Nav:** a floating bar with Create, Templates, Pricing, FAQ, Log in and Sign up. Login, sign-up and password reset open as a dialog.
- **Popup URLs:** every popup has its own address, `?dialog=<name>`, so it survives a refresh, can be shared, and the browser's Back button closes it. Opening a popup adds a history entry; closing it removes the parameter.
  - `/?dialog=templates`: template chooser (works from any page: the nav and footer link here).
  - `/?dialog=login`, `signup`, `forgot`: the account dialog (works on every page, including `/privacy` and `/terms`).
  - `/?dialog=preview`: the preview popup opened by Download PDF for Guest/Free: the invoice with its watermark, plus "Remove watermark & download" and "Download FREE" buttons.
  - `/?dialog=download`: the "Remove the watermark" dialog, $0.99 (Guest and Free only; Pro accounts just close it).
  - The password-reset, email-verify and Stripe return links keep their one-time `?reset=`, `?verify=` and `?checkout=` parameters, which are removed from the address bar once read, because they carry secrets.
  - Logic lives in `frontend/lib/dialog-url.ts`. Add a name to `DIALOGS` there for a new popup.
- **Legal pages:** the text lives in `frontend/app/privacy/page.tsx` and `frontend/app/terms/page.tsx`. It describes what the app does today (accounts, Stripe, 48-hour guest invoices, hashed IPs on sessions), so update it if that changes. Set `NEXT_PUBLIC_SUPPORT_EMAIL` to show a contact address on both pages. Have a lawyer review them before launch.
- **Stripe and email links:** these return to `/` with a query string (`?checkout=success&invoice=...`, `?billing=success`, `?verify=...`, `?reset=...`), which the page handles.

### How designs map to downloads

Any visitor can switch templates to look at them. What lands in the PDF is enforced by the server:

- **Guest and Free:** the PDF is always Classic, as customized on the invoice itself (`layout` and the logo are sent with the invoice and stored in `invoices.layout_json` / `invoices.logo_png`), with the branding footer and a watermark until it is paid off. The server never trusts a client-chosen template for them.
- **Pro:** each design is saved as one of the account's own templates (created on first use), so the PDF matches the editor exactly, including the logo, with no watermark. Download PDF downloads straight away (Pro and paid-off invoices); Guest/Free first see a preview popup with the watermark and choose to pay or download free.

Fonts and colors apply to the whole invoice. The PDF engine has one font family and one color set per template, so per-element size, bold and italic are not available yet.

## Scope notes and next steps

These parts of the brief are not done yet, or were implemented differently:

- **No dashboard page:** invoices are autosaved to the account and the editor reopens the one you were last working on in this browser, but there is no list of past invoices yet. The API for it (`GET /api/v1/invoices`, with search and CSV export for Pro) is there.
- **Guest logos aren't persisted:** a logo uploaded before signing in is a browser-only preview. It is uploaded to the account's template when the user is Pro. The draft text and design are kept in `localStorage`.
- **Per-element text styling:** see "How designs map to downloads" above.

- **Google OAuth:** not implemented. Email and password, verification and reset are complete.
- **Recurring or scheduled invoices (Pro):** not implemented. The natural next step is a `recurring_schedules` table plus a job in `jobs.rs`.
- **PDF fonts:** the standard PDF fonts cover Latin text. Other scripts are transliterated or replaced with `?`. To fix this, embed a Unicode TTF such as Noto Sans with `add_external_font` in `pdf.rs`.
- **Background work:** emails go through an in-process queue (tokio mpsc) and are delivered with the Resend HTTP API. PDFs render inline because they take milliseconds. Move to a Redis-backed queue (for example `apalis`) if a durable queue becomes necessary.
- **Guest drafts:** these are stored in `localStorage` plus an hourly-cleaned Postgres row, not in the Redis `invoice_draft:*` key from the brief. A Postgres row is needed anyway so payments can reference the invoice.
- **SQL checking:** queries use sqlx runtime-checked parameterized calls. Switching to the `query!` macros, with `cargo sqlx prepare` in CI, would add compile-time checking.
- **Email column:** emails are lowercased and stored in a unique `text` column instead of `citext`, which avoids driver type-mapping issues.
- **Observability:** structured JSON logs (`tracing`) and request ids are in place. OpenTelemetry export, Prometheus metrics and Sentry still need to be connected to your providers.
- **Next.js CSP:** the web app's CSP allows `'unsafe-inline'` scripts, which Next needs without nonces. A nonce-based CSP in middleware would tighten it.
